# Step 4 — rulings and deferred follow-ups

Decisions made on the owner's behalf while building the browser frontend (a React app in the sandbox, recorded from inside the browser through `@stackvibed/browser`, spec `docs/superpowers/specs/2026-10-31-step-4-frontend-design.md`), and minor review findings deliberately deferred. Source: the execution ledger (deleted after completion). Branch `step-4-frontend`.

## Rulings

- Ruling F1: no zone.js and no user-interaction instrumentation; the SDK records actions with its own capture-phase `click`/`submit` listener on `document` (INTERNAL `stack.action` spans) and page loads and route changes with its own `stack.navigation` spans (kind `load` or `route`), so the reporter recognises browser spans by these span names, not by the `telemetry.sdk.language = webjs` resource attribute (spec §3.3) — why: this resolves the spec §7 spike without code: OTel's user-interaction instrumentation describes the element the listener is attached to, which under React's root event delegation is the root container, not the clicked button, and `ZoneContextManager` cannot follow native `async`/`await`, so a fetch is not parented to its click; the §5.2 fallback (a fetch with no ui parent nests under the latest ui step of its component that started before it) is therefore the main path, a parent-span link still being honoured when present — cost if wrong: a fetch started long after a click (a timer, a late effect) still nests under that click; an app that needs exact causality would need its own context propagation.
- Ruling F2: `GET /stock` answers `[{"sku": …, "available": …}]`, the stock table's column, not `quantity` as the spec says — why: it is what `StockRepository` already reads (`available`), and renaming the field for the spec's wording would only add a mapping — cost if wrong: one field name in `StockController` and the stock list.
- Ruling F3: the frontend's `package.json` does not list `@stackvibed/browser`; the Gradle task `installStackBrowser` runs `npm install --no-save ../../build/stack-browser/stack-browser.tgz` after `npmInstall` (spec §3.1 says a `file:` dependency) — why: the tarball changes on every tool build and a `file:` dependency locked in `package-lock.json` then fails npm's integrity check; `--no-save` has no hash to mismatch — cost if wrong: a plain `npm install` in `services/frontend` prunes the package (documented in the README: build through Gradle); `installStackBrowser` always runs (`upToDateWhen { false }`).
- Ruling F4: ui steps draw a request arrow only (no response row) and never fail — why: a page load or a click has no reply to draw; the failure of what it triggers belongs to the fetch hop under it — cost if wrong: a ui step cannot show a duration of its own on a response row (its duration is in the details panel).
- Ruling F5: work on branch `step-4-frontend` in the main checkout instead of a new worktree — why: the branch already existed there, and the owner's uncommitted `sandbox/stack/boards/primary.layout.json` edit and `.claude/` stay untouched (implementers never staged them) — cost if wrong: none; a worktree could still be cut from the branch.
- Ruling F6: Task 1 (`StackBrowser`) omits `testImplementation(libs.mockk)` that the plan listed — why: the `stack.kotlin-library` convention plugin already puts MockK on every module's test classpath — cost if wrong: none (the test would not have compiled).
- Ruling F7: `sandbox/services/frontend/nginx.conf` adds `Vary: Accept` to `/index.html` and to the `/orders` proxy location (not in the plan) — why: without it the browser's HTTP cache served the `/orders/<id>` HTML page to the app's own JSON fetch of the same URL after a reload; the acceptance test `order page survives a reload` caught it — cost if wrong: none; a reload of an order page would show the wrong body.
- Ruling F8: the browser acceptance tests wait for the event counts of the real recordings, not the plan's lower values: `browse-stock` 6, `place-order-in-browser` 29, `place-order-out-of-stock-in-browser` 13 (the service tests keep 11, 9 and 2); the out-of-stock test first waited for 8 until Task 6 retuned it — why: with fewer events the test could read the recording before the services' spans arrived (spans are exported in batches); the counts break down in the acceptance test's comments (e.g. `place-order-in-browser`: 3 ui navigations, 3 ui actions, 3 frontend fetches, 4 server spans, orders-service's call to inventory-service, 4 database calls, 11 methods) — cost if wrong: the counts are exact, not lower bounds with margin, so a changed number of traced methods or fetches makes `awaitRecording` wait to its 10 s timeout instead of failing fast.
- Ruling F9: `@stackvibed/browser` uses `@opentelemetry/sdk-trace` 2.12.0 instead of the plan's `sdk-trace-web` and `sdk-trace-base` — why: npm marks both deprecated at 2.12.0 ("Use @opentelemetry/sdk-trace") and the OTLP exporter already depends on `sdk-trace`; the new package has no `register()`, so the SDK sets the three globals itself (`StackContextManager` as the context manager, a composite of the W3C trace-context and our baggage propagator, the tracer provider); the context manager is required, without it `context.with` is a no-op and the fetch instrumentation injects no `traceparent` — cost if wrong: a dependency swap later.
- Ruling F10: no `semconvStabilityOptIn` option — why: `@opentelemetry/instrumentation-fetch` 0.223.0 has no such option and already emits only the stable HTTP names (`http.request.method`, `url.full`, `server.address`, `server.port`, `http.response.status_code`, and `error.type` for status ≥ 400), which the browser test asserts — cost if wrong: none; the test pins the names (`error.type` on a fetch with no response is the SDK's own, Ruling F17).
- Ruling F11: the browser tests that use the real exporter (posts protobuf, export on `pagehide`, a failing reporter only warns) post to a local Node HTTP server answering CORS the way the reporter does (`POST`, `Content-Type` only), instead of Playwright's `page.route` — why: Playwright routing ends with the page, so it cannot see the keepalive fetch of the `pagehide` export; the fixture also pins that the preflight asks for `content-type` only; the 503 fixture sends `Retry-After: 0` so the test does not wait out the exporter's backoff — cost if wrong: none.
- Ruling F12: `@opentelemetry/semantic-conventions` is overridden to 1.43.0 in `tool/browser-sdk` and in the frontend's `package.json` — why: the transitive `^1.29.0` would resolve to 1.44.0, three days old when pinned, and the pins follow the two-week rule; the SDK's own lock does not apply to a frontend installing the tarball, so the frontend repeats the override — cost if wrong: none.
- Ruling F13: `window.__STACK_FLUSH__` waits for spans that have started and not ended (tracked by `StackSpanProcessor` `onStart`/`onEnd`), at most 1000 ms, and then force-flushes; `StackBrowser.flush(page)` calls it; there is no sleep in `FrontendScenarios`; `pagehide` flushes at once without waiting — why: instrumentation-fetch ends the fetch span 100 to 300 ms after the response (it waits for the resource-timing entry), so a flush right after the page rendered exported the navigation and action spans but not the fetch, and the closed page lost it (three acceptance tests failed with no `http.client` from `frontend`); pinned by the browser test `flush waits for a fetch still in flight` and a unit test; this reopened the finished Task 5, as Review Focus 1 depends on it — cost if wrong: a flush takes up to 300 ms longer after a fetch, up to 1 s when a fetch hangs or when called before the window `load` event.
- Ruling F14: after Task 7's review, three minors went through one fix round before Task 8: (1) the observed-vs-curated merge in `TopologyService` no longer lets an observed service beat a curated `frontend` (it was `putIfAbsent`), so a frontend stays a frontend whatever is seen first (Review Focus 5); (2) the run-6 fixture's POST response, method events and DB events carry the same order id the frontend navigates to; (3) the run-6 event clock agrees with its manifest — why: 2 and 3 would have been copied byte-identical into viewer-ui's e2e fixture by Task 8 — cost if wrong: one small extra round; two other minors were deferred (below).
- Ruling F15: Task 8 fixes the viewer-ui board-edge flake in `PrimaryBoard.tsx` (outside its file list): the layout effect depended on `persist`, whose identity changed when the canvas mounted, so ELK ran again and replaced the measured nodes (the e2e `board shows components and highlights create-order` failed with "edge count 0, expected 2" about 4 runs in 60); the effect now reads a `persistRef` (0 failures in 150 runs) — why: a real race, first seen in Task 5's full build and reproduced with a trial loop — cost if wrong: none; there is no automated regression test, only the loop.
- Ruling F16: ui spans (actions and route changes) start at `Date.now()`, the clock the fetch instrumentation starts its spans on (sdk-trace takes `Date.now()` when no start time is given), instead of `hrTime()` (`performance.timeOrigin + performance.now()`, sub-millisecond); the load span still starts at `performance.timeOrigin` (epoch milliseconds) — why: on two clocks the POST a submit handler starts appeared to start before the submit (submit at …828.2999 ms, its fetch at …828.000 ms), so `uiStepOf` nested it under the click on the submit button or under `load /order` (4 of the 7 real POSTs of the last acceptance run); on one millisecond clock the fetch starts no earlier than its action, and the ties within a millisecond (click, submit and fetch in one millisecond is common) go to the later ui event in the list, which is the submit: the click and the submit it triggers end in dispatch order in one task, so they are in one export batch in that order, and the OTLP encoding, the reporter (one append per export, in span order) and the viewer (the events file in line order) keep it; pinned by the browser test `a fetch started in a submit handler starts no earlier than the submit, …` (5 sends, exported click then submit), `FlowBuilderTest` `a POST its submit handler starts nests under the submit, on the timestamps of real runs`, and the acceptance tests (the POST starts no earlier than the submit; actions in recording order) — cost if wrong: ui steps lose sub-millisecond precision (two actions within one millisecond are ordered by the list, not by time); recordings made before this fix keep their misnested POSTs; a batch split between a click and its submit (only past 512 queued spans) could reorder them.
- Ruling F17: a fetch that got no response (network error, abort) gets `error.type` from the SDK — `applyCustomAttributesOnSpan` sets the error's name (`TypeError`, `AbortError`; `Error` when it has none) when the result is not a `Response` — and the reporter records the `http.response.status_code = 0` that instrumentation-fetch 0.223.0 writes for it as no status — why: the instrumentation writes status 0 and no `error.type`, so the reporter recorded `status = 0, errorType = null` and the viewer showed the failed fetch as an ok `0`; with `status = null` and an `errorType` the viewer already shows it failed, with the error's name; pinned by the browser test `a fetch that gets no response records its error type` (`page.route(…).abort()`), `SpanEventMapperTest` `browser fetch that got no response has null status and keeps its error type`, and the viewer-ui `status.test.ts` case for a frontend fetch — cost if wrong: a server answering a real status 0 cannot exist, so none for HTTP; a JVM client span with status 0 (none seen) would also lose it.

## Deferred follow-ups

- Cross-origin APIs: only same-origin fetches get `traceparent` and `baggage` (so the services' spans join the run); a frontend that calls another origin needs the SDK to propagate to an allow-list and the service to allow those headers.
- Frameworks other than a React SPA (the package is framework-neutral, only React is tested), and Firefox and WebKit (only Chromium).
- JS errors, console logs and Web Vitals as events; browser-side body capture; level 2 inside the browser.
- A "user" actor distinct from the e2e client: every ui step is drawn from `e2e-client`, also in a manual run.
- A hung fetch (never ends) stays in the processor's open set, so every later flush pays the 1 s cap; give open spans a deadline.
- `error.type` on a failed browser fetch is now set and tested for a fetch with no response (Ruling F17: browser test, mapper test, viewer-ui status test); the instrumentation's own `error.type` for a status ≥ 400 is still not asserted by a browser test, and the load span's timing and `readyState` branch, the `replaceState`/`popstate` routes and an idempotent second `startStackRecording` remain untested.
- Fetch-only runs: a frontend whose run has fetches but no ui events (the recording started after the page's actions, or the app records no actions) is not recognised as a frontend in that run: its fetches fall back to host naming (`localhost`, not the API's first path segment) and the component is typed `service` in that run's discovery.
- Derive the viewer run-6 fixture (`tool/viewer-backend` and `tool/viewer-ui` e2e) from a real recording instead of hand-written events, so it carries the real clocks and event order (ui spans on the millisecond clock, click before submit in one millisecond).
- `describeTarget` goes beyond its documented rule: it collapses inner whitespace and trims the end after the 80-character cut; an empty `data-testid=""` stops the `closest()` walk, and a null target gives an empty target. Align the rule (spec, Global Constraints) or the code.
- The tarball name `stackvibed-browser-0.1.0.tgz` is hard-coded in `tool/browser-sdk/build.gradle.kts` and can drift from `package.json`; the sandbox's `installStackBrowser` declares `inputs.file` but is never up to date, and spells the tarball path in three places.
- Mixed components (ui steps and server requests in one component) lose owner nesting for their client calls, and `uiStepOf` re-sorts the ui steps for every fetch.
- The run-6 fixture's folder name (`2026-10-31…`) disagrees with its manifest `startedAt` (`2025-10-09`), and `createdAt` in its bodies is 2026-10-30; cosmetic.
- The order form does not disable its submit button while a request is in flight, so a double click places two orders.
- The Playwright lifecycle is duplicated between `FrontendE2ETest` and `SandboxAcceptanceTest`.
- `StackAttributes.java` has a Javadoc line over 100 characters; the comment "version 3 lines still read" says the line comes from the golden file, but it is now an inline adapted sample; `navigationDraft` and `actionDraft` repeat the common-field block, as the existing drafts do; `UiFacts` takes the wide event type; the doc comment in `layoutSequence.ts` is long.
- Owner try-out, not yet looked at in a browser: the `frontend` node colour, the ellipsis on long edge chips, and how the `ui` edges look on the board.
- Test polish, left as is: the `flush` "no SDK hook" branch lives in a JS string and is not covered by the mock test, and the `tag` test checks `addInitScript` at least once, not exactly once; `FrontendE2ETest.closePage` masks an `openPage` failure (a `lateinit` error); `CorsTest` covers the preflight only, not the header on the actual POST, and the "control api has no cors" test asserts only the absent header; the browser fixture's spans are all roots in one trace; browser tests 4 to 6 are weak (test 4's "no `traceparent`/`baggage`" asserts are vacuous for a cross-origin URL, test 5's preflight loop passes when no `OPTIONS` arrived, test 6 can pass without `pagehide` through the 200 ms timer, and our own `pagehide` listener is unpinned); the `HopDetails` ui test does not assert the navigation duration; the `persistRef` fix has no automated regression test.
